# 线程池方案性能测试报告（单元测试方式）

日期：2026-02-26  
项目：`project-2026`  
测试方式：JUnit 单元测试（微基准风格，含预热 + 固定迭代）  
测试类：`ThreadPoolSchemePerformanceTest`

## 1. 测试目标

- 对方案 A/B/C/D 的 `reconcile` 核心路径做统一口径的性能对比。
- 验证在相同测试规模下，各方案的平均单次开销与吞吐能力。
- 建立可持续回归的性能基线（后续改动可直接复跑对比）。

## 2. 测试方法

- 每个方案执行：
  - 预热：`5,000` 次
  - 正式迭代：`50,000` 次
- 统计指标：
  - 总耗时（`elapsedMs`）
  - 平均单次耗时（`avgNs`）
  - 吞吐（`opsPerSec`）
- 统一断言：
  - 平均单次耗时需小于 `2,000,000 ns`（2ms），用于防止明显性能退化。

执行命令：

```powershell
mvn "-Dtest=ThreadPoolSchemePerformanceTest" test
```

## 3. 测试结果（本次实测）

| 方案 | elapsedMs（50k次） | avgNs（单次） | opsPerSec |
|---|---:|---:|---:|
| 方案 A（规则驱动） | 5.562 | 111.248 | 8,988,925.64 |
| 方案 B（反馈闭环） | 7.964 | 159.280 | 6,278,252.13 |
| 方案 C（两层混合） | 17.431 | 348.628 | 2,868,386.93 |
| 方案 D（建模推断） | 19.611 | 392.220 | 2,549,589.52 |

排序（快 -> 慢）：A > B > C > D

## 4. 结果解读

- 方案 A 最快，逻辑最简单，计算路径最短。
- 方案 B 在引入状态与控制判断后，开销略增，但仍处于高吞吐区间。
- 方案 C 因预算层 + 控制层双阶段决策，开销高于 A/B。
- 方案 D 增加模型推断与门控流程，平均开销最高，但仍远低于 1 微秒级别阈值上限（本次约 392ns/次）。

## 5. 结论

- 四个方案均通过性能单测门槛，未发现性能回归风险。
- 若优先追求极致执行效率，A/B 更有优势。
- 若优先追求动态能力与控制精度，C/D 的额外开销在当前量级可接受。

## 6. 注意事项

- 当前结果属于“单机、单进程、测试环境”的相对对比，不等同线上端到端延迟。
- 微基准对 JVM 状态敏感，建议在 CI 中做多次复测并统计均值/分位数。
- 建议后续补充：
  - 不同并发度下的吞吐曲线；
  - 队列高水位场景下的性能对比；
  - 长时间运行（>10分钟）稳定性回归。

## 7. 并发压测补充（8线程）

新增测试类：`ThreadPoolSchemeConcurrentPerformanceTest`  
执行命令：

```powershell
mvn "-Dtest=ThreadPoolSchemeConcurrentPerformanceTest" test
```

测试参数：
- 并发线程数：`8`
- 每线程操作数：`10,000`
- 总操作数：`80,000`

并发实测结果：

| 方案 | totalOps | elapsedMs | avgNs（单次） | opsPerSec |
|---|---:|---:|---:|---:|
| 方案 A（规则驱动） | 80,000 | 13.482 | 168.521 | 5,933,969.75 |
| 方案 B（反馈闭环） | 80,000 | 47.666 | 595.830 | 1,678,331.07 |
| 方案 C（两层混合） | 80,000 | 71.099 | 888.731 | 1,125,199.55 |
| 方案 D（建模推断） | 80,000 | 134.968 | 1,687.100 | 592,733.09 |

并发排序（快 -> 慢）：A > B > C > D

结论补充：
- 在并发压力下，四个方案仍满足本次门槛断言（吞吐均 > 200k ops/s）。
- 复杂策略（C/D）的并发开销明显高于 A/B，但依然处于可接受区间。
